# Replays and frame hashes

The player can record the input of a session, play it back exactly, and write
a hash of every frame it shows. Playing the same recording in the Allegro build
and in zplayer and diffing the two hash logs proves that zplayer renders the
same frames, or shows the first frame where it does not.

Everything here is opt-in through command-line switches. Without them the
player behaves exactly as before; every hook in the game code returns at once.

## Switches

| switch | what |
|---|---|
| `-record FILE` | Record the input to FILE while you play. |
| `-replay FILE` | Play FILE back. The game exits when the recording ends. |
| `-framehash FILE` | Write one line per frame: frame number, hash of the 256x224 picture, hash of the palette. Works with or without a recording. |
| `-frames N` | Exit after N frames (recording, playback or live). |
| `-unthrottled` | Do not wait for the 60 Hz frame timer (and skip `use_dwm_flush`). Playback then runs as fast as the machine allows. Not saved in zc.cfg. |
| `-replay-seed N` | While recording, seed the random numbers with N instead of the clock. |
| `-framedump DIR FIRST LAST` | Save frames FIRST..LAST as 8-bit BMP files `DIR/frame000123.bmp` (DIR must exist). For looking at a frame the hashes flag. |

`-record` and `-replay` cannot be combined. The other switches of the player
(`-notitle`, `-load`, `-slot`, `-fast`, ...) still work, but a recording must be
played back with the same ones it was made with (the header has a comment with
the switches used).

Exit status of the player when a recording or `-frames` ends it: 0 done,
1 done, but the playback reported warnings (a desync, or a zc.cfg that differs
from the recording's), 2 bad switch or file, 3 stopped because the game opened
a menu or dialog (see Limitations). Messages go to stderr and allegro.log;
playback warnings also go into the hash log.

## Comparing zplayer with the Allegro build

```
python -I tools/replay_run.py --exe <allegro build>/Release/zelda.exe --data "<game data folder>" ^
       --replay tests/replay/1st_quest_walk.zcr --hashlog allegro.txt --unthrottled
python -I tools/replay_run.py --exe <zplayer build>/zplayer.exe --data "<game data folder>" ^
       --replay tests/replay/1st_quest_walk.zcr --hashlog zplayer.txt --unthrottled
python -I tools/replay_compare.py allegro.txt zplayer.txt
```

`replay_run.py` copies the player, the DLLs next to it (and `alleg44.dll` from
the data folder if needed), the game data (`zelda.dat`, `fonts.dat`, `sfx.dat`,
`qst.dat`, `1st.qst`..`5th.qst`, `zelda.nsf`, `Classic.nsf`, `5thmusic.nsf`),
a zc.cfg and an **empty zc.sav** into a new temporary folder, runs the player
there and copies the hash log out. The default zc.cfg is

```
[zeldadx]
fullscreen = 0
window_display = 3
```

(`--cfg FILE` uses another one, `--quest FILE` copies a custom quest, `--frames`,
`--framedump`, `--keep`, `--run-dir`, and extra player switches after `--`.)
Runs must be sequential: the player refuses to start while another copy runs.

`replay_compare.py` prints `IDENTICAL` (exit 0) or the first differing frame,
whether the picture, the palette or both differ, how many frames differ and
whether they match again later (exit 1). Then
`--framedump DIR F F` on both players shows the two pictures of frame F.

`tests/replay/1st_quest_walk.zcr` with its expected hash log
`tests/replay/1st_quest_walk.framehash.txt` (made with the Allegro build) is
the reference sample: a new game of the 1st quest from an empty zc.sav (title
screen, registering the name "link", start), into the first cave for the sword
and around the first screens with octoroks and sword beams, 2478 frames. It is
generated by `tests/replay/make_1st_quest_walk.py`. The sample checks against
the expected log directly:

```
python -I tools/replay_run.py --exe zplayer.exe --data "<data>" --replay tests/replay/1st_quest_walk.zcr ^
       --hashlog zplayer.txt --unthrottled
python -I tools/replay_compare.py tests/replay/1st_quest_walk.framehash.txt zplayer.txt
```

## Recording

Start the player with `-record FILE` (and usually `-framehash FILE`) and play.
The recording ends when the game exits, or after `-frames N`. Keep the window
focused and do not open the menu or any dialog (Esc, a click in the window,
F6, F9, F10, the close button): menu input is not recorded, so playback stops
there.

What the game reads is recorded, not raw OS events, at a fixed point of every
frame (the end of `advanceframe()`, after the frame was shown):

- **`key[]`**: the whole array, as the game left it. The game itself clears
  entries (`ReadKey()`), so a held system key fires once, in playback too.
- **The keyboard buffer** (`keypressed()`/`readkey()`, used by the name entry):
  while recording, keys pressed during a frame are held back by a
  `keyboard_callback` and put into the buffer (`clear_keybuf()` +
  `simulate_keypress()`) at the next frame boundary, so the game sees them at
  that frame. Playback serves the same entries at the same frame through
  `install_keyboard_hooks()`.
- **The mouse**: the game only reads it through `gui_mouse_x/y/z/b()`; these
  are replaced by functions returning the state taken at the frame boundary.
- **The joystick**: the game polls it once per frame, in `syskeys()`; the state
  of `joy[joystick_index]` and `num_joysticks` right after that poll is
  recorded and, in playback, written there instead (the joystick driver is
  removed during playback).
- **The random seed**: `init_game()` seeds `rand()` from the clock; the value
  used is recorded and replayed (`-replay-seed` fixes it when recording).

Playback removes the keyboard driver (`remove_keyboard()`, then
`install_keyboard_hooks()`), so nothing typed on the playback window, and no
"release all keys" when the window loses the focus, can change `key[]`.

While recording, Allegro updates `key[]` from its own input thread. A key event
that arrives while the game is computing a frame (between the frame boundary
and the next `updatescr()`) can be seen by the game partway through that frame;
the recording marks such frames (`# N: 1 key event(s) arrived while frame N-1
was computed`) and the end-of-recording message counts them. The playback of
such a recording may then differ from the live session at those frames; it is
still exact and the same every time, in both builds. This window is short (the
game logic of one frame); the keyboard buffer and the mouse are not affected.

`-framehash` and `-frames` also work in a normal (live) session, which is not
deterministic; there the AG logo still waits for a key (`-fast` skips it).

## Determinism

Sources of nondeterminism in a session and what the replay mode (`-record` or
`-replay`) does about them:

| source | handling |
|---|---|
| `srand(time(0))` in `init_game()` (the only `srand`) | value recorded/replayed |
| `rand()` before the first `init_game()` (title screens) | deterministic: the C runtime starts with seed 1 and only the game thread uses it (Allegro has its own generator) |
| frame throttle (`throttleFPS()`, `logic_counter` timer, vsync, DwmFlush) | only waits; one `advanceframe()` is one logic step, so the speed never changes the result (`-unthrottled` removes the wait) |
| keyboard (`key[]`, buffer), mouse, joystick | fixed per frame from the recording, see above |
| enhanced music: `zcmusic->position` counts calls of `zcmusic_poll()`, which a 25 ms timer also makes; the Triforce pickup waits for it | no enhanced music: `zcmusic_init(0)` enables no format, the game falls back to MIDI |
| MIDI position (`midi_pos`: Triforce pickup, title screen) and sample voices (`sfx_allocated()`: the whistle waits for its sound) follow the sound card | no sound driver (as `-s`): `midi_pos` stays negative, no voice is allocated |
| AG logo waits for a key | skipped |
| screen saver after idle time | disabled (`after_time()`) |
| FPS counter (timer) | drawn on the screen, not in the hashed frame |
| zc.sav and zc.cfg | must be the same at the start: `replay_run.py` uses an empty zc.sav and a fixed zc.cfg. The recording header stores the zc.cfg settings that change the outcome (key bindings, joystick buttons, name entry mode, title screen, transparent layers, fast quit, click to freeze, epilepsy option); playback warns when they differ |
| menus and dialogs (Allegro GUI loops) | not recorded; playback stops with status 3 when the game waits in one |

The frame hash is FNV-1a 64 over the 256x224 bitmap `updatescr()` shows (the
game frame after the wavy effect and the no-subscreen panorama, with message
text and the "black opening"; without the FPS counter, the pause text and the
scaling) and, separately, over the r, g, b of the 256 palette entries
(`get_palette()`). The frame number counts frames shown since the start, from 0
(the pause loop counts too).

## File formats

Recording (`.zcr`, text, one event per line, ordered by frame; `#` starts a
comment):

```
zcreplay 1
cfg <setting> <value>                 zc.cfg settings at record time (checked)
<frame> key <KEY_NAME|scancode> <v>   key[scancode] = v from this frame on
<frame> char <value>                  keyboard buffer entry for this frame (readkey() format: scancode << 8 | ASCII)
<frame> mouse <x> <y> <z> <b>         gui_mouse_x/y/z/b() from this frame on
<frame> joy <poll> <num_joysticks> <buttons> <pos d1 d2 x 15>
                                      joystick after the poll-th poll_joystick() of the frame
                                      (-1: before the first frame); buttons is a bit mask,
                                      then pos d1 d2 for stick 0..4, axis 0..2
<frame> seed <value>                  srand() value of init_game() in this frame
end <frames>                          number of frames; playback exits after them
```

Key names are the Allegro `KEY_` names without the prefix (`UP`, `ENTER`, `A`,
`0_PAD`, `LCONTROL`, ...). Numbers may be decimal or `0x` hex. Input written for
frame N is what the game reads while it computes frame N. Recordings are easy to
write by program; see `tests/replay/make_1st_quest_walk.py`.

Hash log (text):

```
zcframehash 1
<frame> <picture hash, 16 hex digits> <palette hash, 16 hex digits>
# warning at frame N: ...      desync warnings of a playback
# stopped at frame N: ...      why a playback stopped early
# end <frames> frames
```

## What zplayer has to match

The replay hooks are in the game code (`src/replay.cpp`, hooks in `zelda.cpp`
and `zc_sys.cpp`) and use only the Allegro API, so zplayer runs the same code.
For identical hashes zcport must behave like Allegro in these points:

- Keyboard, checked by `tests/conformance/test_replay_sdl_keyboard.cpp`:
  `keyboard_callback` is called for every key put into the buffer, simulated
  ones included, and a return of 0 drops the key; `clear_keybuf()` empties
  what `simulate_keypress()` put in; with `install_keyboard_hooks()` set,
  `keypressed()`/`readkey()`/`ureadkey()` use the hooks and **`clear_keybuf()`
  empties the hooked buffer by calling them** (Allegro does; the zcport
  foundation did not when this was written).
- With no keyboard driver (after `remove_keyboard()`), OS key events must not
  change `key[]` (the zcport foundation's `zcport_key_down()` still did), and
  `poll_mouse()` should let the platform process its window events: playback
  calls it once per frame, since the unthrottled playback skips `rest()` and
  replaces the `gui_mouse_*()` functions.
- `gui_mouse_x/y/z/b` are assignable hooks that the game and the GUI call.
- After `remove_joystick()`, `poll_joystick()` fails and leaves `joy[]` alone;
  `num_joysticks` and `joy[]` are writable.
- Without `install_sound()`: `play_midi()` leaves `midi_pos` negative and
  `allocate_voice()` returns -1.
- The zplayer replacement of `zcmusic.cpp` honours the flags of
  `zcmusic_init()`: with 0, `zcmusic_load_file()` returns NULL for every format.
- `get_palette()` returns the palette last set; `save_bmp()` writes 8-bit BMPs.
- The game's `rand()` sequence: zcport must not call the C library `rand()` on
  the game thread, and a port to another C library (Android) needs a `rand()`
  with the MSVC generator and `RAND_MAX` (0x7FFF) for its hashes to match.

## Limitations

- Menus and dialogs: not recorded; playback stops when the game waits in one.
  The name entry and the in-game screens (game over, save, subscreen) are fine.
- The name entry's Esc handler busy-waits for Esc to be released
  (`register_name()`), which a playback never does: do not press Esc there.
- ZScript that sets the mouse position (`Link->InputMouseX = ...`) moves the
  real mouse; the script sees the new position from the next frame on (in
  recording and playback alike, but not as in a normal session).
- No sound or enhanced music in replay mode.
